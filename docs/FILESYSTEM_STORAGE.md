# Файловое хранилище без MinIO

Runtime: API, worker, PostgreSQL/PostGIS, TiTiler. База остаётся на сервере; подключение NAS относится к файлам. Локальная установка использует обычные файлы в Docker-томе `local_work`.

## Каталоги NAS

```text
botplusmaps/
  projects/<проект>/                 # оригиналы, приложение читает их без записи
  system/work/
    media/panoramas/ab/cd/<uuid>_<имя>.jpg
    media/orthophotos/               # файлы прежних импортов и их превью
    import-staging/                 # исходники веб-импорта растров
    import-products/                # подготовленные COG
    legacy-uploads/                 # совместимые рабочие пути старого профиля
    temp/                           # временные файлы и multipart-spooling
    tasks/                          # статусы прежних операций
```

`MEDIA_ROOT=/app/data/media`. Файлы фотографий и панорам размещаются в `panoramas`; отдельной новой модели фотоколлекций этот этап не добавляет. Современный растровый импорт сохраняет ссылки на разрешённые исходники в PostgreSQL: готовый COG может читаться напрямую из `projects/`, без копии. Неконвертированный GeoTIFF сохраняется как исходник, производный COG создаётся отдельно. Выбор CRS не переписывает оригинал.

## Подключение

Сначала смонтируйте NAS на хосте, создайте каталоги и проверьте чтение/запись от UID приложения 10001. Для LXC предпочтительно монтировать NFS на Proxmox и передавать отдельные bind mounts в контейнер: источники RO, рабочий каталог RW. Не менять squash/ACL всего NAS ради приложения.

В закрытый `.env.local` добавьте пути хоста, запускающего Docker:

```dotenv
NAS_SOURCE_DIR=/srv/botplus/sources
NAS_DATA_DIR=/srv/botplus/work
NAS_UPLOADS_DIR=/srv/botplus/work/legacy-uploads
```

```sh
mkdir -p /srv/botplus/work/legacy-uploads /srv/botplus/work/temp
# Источник /srv/botplus/sources уже должен быть подключён с NAS.
docker compose --env-file .env.local -f compose.local.yml -f compose.nas.yml config --quiet
docker compose --env-file .env.local -f compose.local.yml -f compose.nas.yml up --build -d
```

Одинаковые пути `/sources/local` и `/app/data` обязательны в API/worker/TiTiler. БД остаётся в `local_postgres`, TiTiler не публикует порт. Overlay не меняет loopback-доступ приложения; LAN/HTTPS настраиваются отдельно.

`create_host_path: false` запрещает Docker создавать отсутствующие папки, но не отличает размонтированный NAS от существующей локальной папки. Перед Docker/стеком нужна host/systemd-проверка ожидаемого NFS-источника и прав; для контейнера 115 такая проверка настроена отдельно. Не запускать запись при отсутствующем NAS. При обрыве NFS hard mount может ожидать восстановления связи.

## Переход с прежнего MinIO

1. Остановить API и worker, дождаться окончания записей. Сделать копию PostgreSQL и закрытой конфигурации; сохранить прежний образ/Compose/тома. Убедиться, что NAS подключён.
2. Использовать **прежний образ приложения**, содержащий SDK `minio`, с кодом `scripts/migrate_minio.py` и `server/storage.py` из этого изменения. Передать прежние `MINIO_ENDPOINT`, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, при необходимости имена бакетов, через закрытый env-файл. Подключить новый каталог данных. Не помещать ключи в историю команд.
3. Проверить план и выполнить копирование внутри этого контейнера:

```sh
python scripts/migrate_minio.py --target /app/data/media
python scripts/migrate_minio.py --target /app/data/media --apply
```

Скрипт копирует текущие объекты `panoramas` и `orthophotos` в одноимённые каталоги, сохраняя ключи из БД. Сверяет размер и SHA-256. Повторный запуск проверяет совпадающие файлы; конфликт содержимого или небезопасный ключ останавливает перенос. Все старые писатели должны оставаться остановлены до переключения. Исторические версии объектов, незавершённые multipart-загрузки и S3-политики не переносятся. SDK нужен только утилите миграции, в новом runtime его нет.

4. Если прежняя установка хранила файлы напрямую в `ORTHO_FOLDER`, скопировать их в `MEDIA_ROOT/orthophotos` с проверкой контрольных сумм и без перезаписи конфликтов. Не переносить временные файлы как зарегистрированные объекты.
5. Запустить новый образ и Compose без MinIO. Проверить существующие панорамы, загрузку новой фотографии, скачивание, COG-тайлы и очередь. Сначала проверить на тестовой установке.
6. Остановить старый MinIO; оставить его том для отката. Не использовать `down --volumes` и `--remove-orphans` при миграции. После новых записей простой откат старого образа уже недостаточен: сначала нужно вернуть новые файлы и согласовать каталог.

Старые прямые S3-ссылки перестанут работать. Доступ остаётся через API и публикации карт.

## Проверка и копии

Резервировать PostgreSQL, `projects/`, весь `system/work/` и закрытую конфигурацию. Файлы в staging/products могут использоваться зарегистрированными слоями — не чистить их по возрасту. Согласовывать снимок базы и файлов, проверять восстановление. Автоматические backups/reconciliation этот этап не добавляет.

Проверки изменения: атомарная запись без перезаписи, защита путей и symlink, bounded-memory copy, Range/206, повторяемая проверяемая миграция, реальный PostGIS-каталог панорам и существующая очередь GDAL. Производительность на терабайтах/миллионах файлов требует отдельного нагрузочного тестирования.

## Просмотр фото и панорам

Обычные снимки отображаются плоско с сохранением пропорций и увеличением. Сферический просмотр используется для полных панорам 2:1 (GPano или крупный equirectangular экспорт). Для неоднозначного снимка 2:1 можно выбрать «Фото». Кадрированные панорамы другого формата отображаются как фото до отдельной подготовки. Разрешение сферической геометрии берётся из файла, а не фиксируется в 4000 пикселей. `display_name` в API скрывает технический UUID/путь; `filename` остаётся совместимым ключом хранения.
