# Скорость отображения ортофотопланов

## Что изменено

- Карта запрашивает PNG 512×512 при zoom URL на единицу меньше zoom карты.
  Наземный размер пикселя совпадает с прежними PNG 256×256: это объединение
  запросов, а не уменьшение разрешения. Для обзора мира поддерживается native zoom 1.
- Во время перемещения карта дожидается остановки, при масштабировании не запускает
  промежуточные наборы тайлов. Порядок, прозрачность и границы слоёв сохраняются.
- Готовые PNG сохраняются в `RASTER_TILE_CACHE_DIR`, по умолчанию
  `/app/data/cache/raster`. В NAS-развёртывании это NAS, не диск контейнера.
  Дополнительно каждый процесс API держит небольшой кэш в памяти.
- Ключ включает версию алгоритма, источник и его fingerprint, производный файл,
  координаты и размер тайла. Перед любым попаданием в кэш проверяются исходники.
  Изменённый или удалённый исходник даёт ошибку, а не старую картинку из кэша.
- Файловые блокировки объединяют одновременные запросы между процессами.
  Файлы публикуются атомарно; ошибки и неполные PNG не сохраняются.
- Авторизация и проверка опубликованной карты выполняются до чтения кэша.
  Приватные ответы остаются private, публичные — no-store. Отключение публикации
  продолжает запрещать доступ даже к ранее закэшированным тайлам.
- `X-Raster-Cache` показывает MEMORY / DISK / MISS / BYPASS, а `Server-Timing`
  отдельно сообщает время разрешения источника, рендеринга и всей операции.
  Индикатор карты показывает фактическое время последнего набора тайлов и ошибки.

PNG остаётся без потерь; оригиналы, их проекции и COG не переписываются.
Существующая очередь подготовки COG не перезапускается при обновлении API.

## Ограничения кэша

По умолчанию: 32 MiB памяти на процесс API, 16 GiB готовых файлов и до 32768
тайлов на NAS, TTL 24 часа. Диск разделён на 256 ограниченных FIFO-сегментов;
свободное место одного сегмента не увеличивает квоту другого. Квоты учитываются
перед публикацией. Индекс — обычный JSON на NAS, SQLite на NFS не используется.
Кэш расходный; он не входит в обязательный backup исходных геоданных.

Настройки окружения API:

| Переменная | По умолчанию |
| --- | --- |
| `RASTER_TILE_CACHE_DIR` | `<родитель MEDIA_ROOT>/cache/raster` |
| `RASTER_CACHE_MEMORY_MB` | 32 |
| `RASTER_CACHE_DISK_MB` | 16384 |
| `RASTER_CACHE_ENTRIES` | 32768 |
| `RASTER_CACHE_TTL_SECONDS` | 86400 |

Нулевой размер памяти/диска отключает соответствующее хранение. Изменения
применяются после перезапуска API. Источники должны оставаться неизменяемыми:
stat fingerprint не является криптографической проверкой или блокировкой внешнего writer.

TiTiler использует два процесса, лимит 1536 MiB и GDAL cache 64 MiB;
`RASTER_MEMORY` и `RASTER_CPUS` настраивают лимиты локального Compose.
Память процессов и файловый кэш ОС расходуются дополнительно к GDAL cache.

## Воспроизводимые измерения

`scripts/benchmark_rasters.py` запрашивает фиксированные наборы тайлов через API
с шестью параллельными HTTP-запросами. Первый тайл и весь набор измеряются отдельно;
записываются ошибки, объём и SHA-256 PNG, cache state и Server-Timing.
Отчёты содержат приватные координаты тайлов: не коммитьте их в открытый репозиторий.

```sh
python3 scripts/benchmark_rasters.py --server http://server:5580 \
  --username operator --ids 2,5 --zooms 14,17,20 --rounds 3 --output before.json
python3 scripts/benchmark_rasters.py --server http://server:5580 \
  --username operator --manifest before.json --output after-256.json
python3 scripts/benchmark_rasters.py --server http://server:5580 \
  --username operator --manifest before.json --tile-scale 2 --output after-512.json
```

Второй запуск сравнивает прежние 256 px координаты и контрольные суммы. Третий
сохраняет охват и детализацию, объединяя дочерние тайлы; по краям может загрузиться
большая область, как и в реальной карте. Кэш браузера HTTP не участвует в benchmark.
Первый проход после обновления означает промах кэша приложения, а не гарантированно
холодные диски. Кэш ОС/NAS не очищается, фоновые рабочие задания продолжаются.
`--operator` предназначен только для запуска оператором внутри API-контейнера;
токен создаётся в памяти и в отчёт не записывается.

## Результаты на рабочем стенде · 23.10.2026

Измерения выполнены по LAN через API на реальных COG около 5,03 и 27,82 GB.
До обновления каждый запрос снова вызывал TiTiler; готовые COG уже имели overview.
Основной повторяемый сценарий — один большой фрагмент второго ОФП на zoom 17:
35 прежних тайлов 256 px или 12 новых 512 px с тем же наземным размером пикселя.
Шесть одновременных запросов, три последовательных прохода, без HTTP-кэша браузера.

| Сценарий | До | После |
| --- | ---: | ---: |
| Большой фрагмент, первый проход | 13,87 с | 15,03 с (12 MISS) |
| Большой фрагмент, повтор № 1 | 12,42 с | 4,15 с |
| Большой фрагмент, повтор № 2 | 12,88 с | 2,74 с |
| Медиана повторов большого фрагмента | 12,65 с | 3,45 с |
| Медиана 18 проходов небольших фрагментов, zoom 14/17/20 | 4,27 с | 2,67 с |

Повторы большого фрагмента ускорились примерно в **3,7 раза**. Первый проход
не ускорился: после перезапуска TiTiler он оказался примерно на 8% дольше.
Поэтому эти результаты не означают мгновенную загрузку произвольной новой области.
Сокращение числа запросов помогает повторным открытиям; первый рендер остаётся
направлением дальнейшей оптимизации. В серии небольших фрагментов часть тайлов
уже была прогрета основным сценарием; она характеризует смешанную рабочую нагрузку.

Контрольный вариант с прежними 35 тайлами 256 px после обновления: 15,45 с
при первом проходе и 6,17 / 6,60 с при повторах. Это отдельно подтверждает вклад
серверного кэша и сокращения числа запросов. Во всех сериях — ноль ошибок HTTP/PNG.
Все контрольные суммы прежних 256 px тайлов на обоих ОФП и трёх масштабах совпали.
Для трёх выбранных пар 256 px / четверть 512 px совпало 99,89–99,96% RGBA-пикселей,
средняя абсолютная разница канала 0,0011–0,0044 из 255, различий alpha нет.
Небольшое различие выборки связано с другим окном GDAL warp; уменьшения разрешения нет.

Это время получения набора PNG, а не полной загрузки страницы, JS и авторизации.
В браузере отдельно проверены реальное изображение и новый индикатор времени.
Кэш ОС/NAS не сбрасывался; фоновая очередь продолжала работать. Одновременно
лимит памяти TiTiler увеличен с 1 до 1,5 GiB, GDAL cache уменьшен со 128 до 64 MiB,
GDAL threads ограничены одним; число процессов и лимит CPU остались равны двум.
Поэтому сравнение отражает весь пакет изменений. После нагрузки OOM не было.

Полные приватные JSON с координатами и контрольными суммами сохранены на NAS
в `system/work/reports/raster-performance-20261022/`; имя каталога соответствует
началу исходных измерений. Повторяемый инструмент — `scripts/benchmark_rasters.py`.

## Второй этап: объём передачи и подключения БД

Карта использует WebP 90 вместо PNG для экранных тайлов. Размер пикселя и alpha
сохраняются, RGB использует сжатие с потерями. Это только формат показа:
исходник, COG, загрузка оригинала и прежние PNG API остаются без изменений.
PNG-кэш используется при первом создании WebP, если он уже существует; вложенные
блокировки сегментов не берутся. Ключ WebP содержит формат и фиксированное качество,
так что данные разных форматов не смешиваются. Оба формата расходуют общую квоту.

Для API в Compose включён пул PostgreSQL `DB_POOL_SIZE=4` на процесс и DSN.
Каждая операция по-прежнему имеет собственную транзакцию, read-only чтения и
проверку актуальных прав пользователя. Соединение возвращается в пул только после
rollback/commit; неисправные соединения отбрасываются. Ожидание ограничено
`DB_CONNECT_TIMEOUT_SECONDS`. При запуске вне Compose значение по умолчанию 0,
низкоуровневый `Database.connect()` всегда открывает отдельное соединение.
Для транзакционных контекстов с включённым пулом вложенность ограничена его размером.
Не используйте Gunicorn `--preload` для создания подключений в родительском процессе.

Замер WebP: тот же manifest и `--tile-scale 2 --format webp`. Это отдельные ключи
кэша; попадание в ранее созданный PNG не является холодным рендерингом GDAL.

## Потоковая выдача видимого фрагмента

Leaflet сохраняет свою сетку, проекции, границы и порядок слоёв, но получает
видимые WebP одним запросом `/tiles/batch` вместо отдельных HTTP-запросов.
Сервер отправляет NDJSON по мере готовности каждого тайла, не дожидаясь всего набора.
На процесс разрешено до шести параллельных чтений, в одной пачке — максимум 24
тайла одного масштаба. Авторизация/публикация проверяется перед открытием потока,
источник и fingerprint — перед выдачей каждого тайла. Потоки имеют no-store.
Base64 увеличивает объём WebP примерно на треть, но устраняет большую часть
отдельных сетевых обменов. Обычные PNG/WebP endpoints остаются совместимыми.

Карта отменяет ненужную пачку при удалении всех её тайлов; ещё не начатые операции
сервер снимает, текущие чтения могут завершиться в кэш. Blob URL освобождаются.
Проверяются разделённые сетевыми блоками строки, копии тайлов на обёрнутом мире,
ошибки, отмена и правильный URL zoom offset. Бинарные данные не помещаются в React store.
Для обратного прокси требуется отключённая буферизация этого endpoint
(`X-Accel-Buffering: no` уже выставлен); в противном случае первый тайл задержится.

Для стенда с 8 CPU рендереру выделены 4 CPU, 4 процесса и 2 GiB памяти,
GDAL cache 32 MiB на процесс. У локального Compose остаются щадящие defaults;
число процессов и кэш задаются `RASTER_WORKERS`, `RASTER_GDAL_CACHE_MB`.
Замер потока: `--transport stream --format webp --tile-scale 2`.
