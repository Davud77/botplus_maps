# Botplus Maps: дорожная карта self-host GIS

Старт: **21 октября 2026**. План v1.0. Статус: интерфейс рабочего пространства зафиксирован; реализуется первый проход локального импорта M2.

## Продукт, который строим

Устанавливаемая на собственный сервер геоплатформа: загрузить или подключить данные, собрать карту, настроить доступ и удобно работать через браузер. Оригиналы остаются на дисках владельца, NAS или его S3-совместимом хранилище. Для основной работы не требуется аккаунт стороннего сервиса. Интернет нужен для первоначального получения пакетов/образов, если администратор не подготовил offline bundle.

Основные пользователи: человек без GIS-подготовки, инженер с локальными системами координат, оператор загрузки больших архивов и администратор сервера. Простые действия доступны в интерфейсе; сложные настройки показываются по необходимости. Публичная карта — сознательное действие владельца, данные по умолчанию закрыты.

Felt — ориентир понятного сценария «добавить → оформить → исследовать → поделиться», NextGIS — управления ресурсами, серверных GIS-источников, CRS и интеграции с настольными GIS. Заимствуем принципы удобства, а не интерфейс или код. Из других решений учитываем QGIS Server, GeoServer и GeoNode: стандарты обмена и отделение данных от конкретного viewer.

## Реализованный проход импорта — 21 октября 2026

Добавлены no-copy регистрация готовых локальных COG, отдельная подготовка GeoTIFF в COG,
PostgreSQL очередь с lease/retry/cancel, отдельный worker с лимитами ресурсов и общий API
для веба/CLI. Веб-растры прежней формы также переведены на очередь. Проверяются source
roots, stat fingerprint, сохранение оригинала и защита регистрации от опоздавшего worker.
Это часть M2: resumable upload, batch manifests, квоты/GC, версии наборов и надёжный импорт
панорам/векторов остаются следующими задачами. Проверка масштаба на реальных 100+ GB ещё впереди.

## Обязательные принципы

1. **Данные у владельца.** Local disk/NAS и self-host S3 — равноправные адаптеры. Обязательных внешних API, телеметрии и внешних basemap/fonts/glyphs в offline-профиле нет. Внешние источники включаются явно; интерфейс объясняет, какие запросы уйдут наружу.
2. **Оригиналы сохраняются.** Подключённые каталоги монтируются read-only. Производные COG, preview, tiles и manifests — в отдельном writable хранилище. Удаление записи каталога не удаляет внешний оригинал по умолчанию.
3. **Масштабирование через детализацию.** Терабайты растров, миллионы media и десятки миллионов векторов не загружаются в браузер целиком. На каждом масштабе — ограниченное покрытие, агрегаты и подходящая геометрия.
4. **Веб и CLI используют один pipeline.** От источника до проверки, задач, версии и публикации одинаковая модель. Закрытие браузера не отменяет серверную обработку; ошибка worker не теряет задание.
5. **CRS — полноценные данные.** Исходная CRS, операция преобразования, grid-файлы, единицы и точность сохраняются. Угадать местную систему по одному параметру проекции нельзя.
6. **Простая установка и обновление.** Docker Compose для одного сервера, без обязательного Kubernetes. Мастер первой настройки, проверка зависимостей, backup/restore и явная процедура обновления.
7. **Расширение через контракты.** Адаптеры источников, import handlers, processing jobs и rendering profiles имеют версию API и примеры. Произвольный плагин не получает автоматически доступ ко всем дискам.

## Что входит в удобный интерфейс

### Основной рабочий сценарий

«Новый проект → Добавить данные → Дождаться проверки → Проверить положение → Добавить на карту → Оформить → Сохранить». Пользователь видит объём, текущий этап, прогресс и понятную ошибку с действием, которое её исправит. «Готово» означает, что файл проверен и опубликован, а не только принят HTTP-запросом.

Слева — слои с папками, видимостью, порядком и стилем. Справа — свойства выбранного объекта/снимка/панорамы. Снизу — таблица и временная шкала по необходимости. Долгие задачи доступны в одном центре задач; состояние не теряется после перезагрузки страницы. Первая карта открывается на данных проекта, а не на случайном мировом масштабе.

### Функции v1

- Проекты, папки, каталог данных, теги, поиск, thumbnails, журнал импорта, статусы качества.
- Слои, легенда, стили по значению/категории/диапазону, opacity, порядок, масштабная видимость, подписи.
- Выбор объекта, таблица, фильтры, поиск по атрибутам; подробная геометрия только по запросу.
- Ортофото: коллекции, дата, bands/render profiles, nodata, сравнение дат swipe/opacity.
- Панорамы/фото: clusters, preview, track navigation, ориентация, время съёмки, совпадающие координаты.
- Измерения с явно указанными единицами и методом, координаты в выбранной CRS, annotations.
- Сохранённые карты, viewer/editor/admin, локальные ссылки с правами; публичная публикация opt-in.
- Импорт GeoTIFF/COG, GeoPackage/GeoJSON/CSV, затем безопасный pipeline архивных Shapefile; внешние PostGIS и XYZ/WMS/WMTS как явные подключения.
- Экспорт выбранных данных и связь с QGIS; сначала документированный API/XYZ/MVT, затем конкретные OGC API/WMS/WFS endpoints по отдельным проверяемым контрактам.
- Администрирование: диски/roots, место, очередь, лимиты, backup, системное состояние и обновления.

Геоаналитика, сложное совместное редактирование геометрий в реальном времени, 3D/point clouds, field/offline sync и marketplace плагинов — последующие версии. Добавление AI не является условием выполнения базовых GIS-задач и не должно отправлять данные наружу без явного подключения владельцем.

## Хранение и импорт

Три входа в одну систему задач:

| Вход | Для чего | Как работают большие файлы |
|---|---|---|
| Веб | Небольшой/средний набор и разовые загрузки | Chunked/multipart, ограниченная параллельность, resume; File API slices, без `readAsArrayBuffer` всего файла |
| CLI с рабочей станции | Архивы, batch, автоматизация | Тот же API, service token из файла/env, checkpoints, checksum по частям, JSONL summary и ненулевой exit при ошибках |
| Серверный путь / NAS | Сотни GB уже на сервере | `storage_root_id + relative_path`; проверка разрешённого root и symlink; ready COG подключается без копирования; прочие файлы идут в worker |

Порог веб-рекомендации настраивается администратором. Размер файла не выбирает способ хранения автоматически. Импорт по пути запрещает произвольный путь из браузера: сервер принимает только ссылку на разрешённый root и объект. URL-ingest по умолчанию выключен; при включении нужны allowlist и защита от SSRF.

Задание: `created → validating → queued → processing → ready → published`; отдельно `failed`, `cancelled`. В БД сохраняются попытки, heartbeat/lease, исходный fingerprint, checksum, CRS/operation и версия результата. Повтор одной операции не создаёт дубликаты. Публикация атомарна только после готовности manifest и артефактов. Невыполненные/старые partial uploads очищаются по политике.

Оригинал 300 GB не обязан занимать ещё 300 GB только ради включения в карту. Но создание COG из неподготовленного TIFF требует отдельного выхода и scratch. Preflight показывает оценку, её основания и свободное место; универсальное обещание «всегда хватит 2×» недопустимо. Добавление сотен тысяч исходников должно работать пакетами, а не через гигантский browser list.

## Пользовательские CRS

CRS registry принимает EPSG, WKT2, PROJJSON, PRJ/WKT и поддерживаемые PROJ definitions. Встроенная CRS источника сохраняется отдельно от пользовательского override. «Назначить CRS» и «перепроецировать данные» — два различных действия с различными последствиями.

Для местных систем отдельно храним datum/transformation pipeline, grid assets и operation version. PROJ_NETWORK выключен в offline-профиле; нужные grid-файлы администратор устанавливает локально. Отсутствие точной операции отображается как ошибка/неподтверждённая привязка, а не как успешный результат приблизительного ballpark transform. Контрольные точки и допустимая погрешность задаются для инженерных проектов.

Исходник остаётся в native CRS. Для web viewer можно использовать производные в 3857/4326; это не означает поддержку рендера всей карты в любой произвольной CRS. Native-CRS view/печать при необходимости потребует отдельного решения, например OpenLayers; решение принимается после эталонных сценариев. Не обещаем геодезическую точность измерений по одной картинке в Web Mercator.

## Техническая архитектура

- React/TypeScript + MapLibre; UI state в Zustand, серверные данные — bounded cache/query layer.
- Модульный API: auth, projects, catalog, imports/jobs, CRS, styles/maps, feature details. Переход с Flask на другой framework не является целью сам по себе.
- PostgreSQL/PostGIS: canonical data, serving geometry/LOD, spatial aggregates и migrations.
- Martin для контролируемых MVT sources; PMTiles для подходящих статичных версий. Изменяемые/закрытые фильтруемые слои обслуживаются с проверкой прав, а не общим публичным архивом.
- TiTiler/GDAL/PROJ: COG/mosaics и подготовка; local files доступны через контролируемый shared mount и реестр, S3 — через собственные credentials сервиса.
- Раздельные API, workers и tile services; долговечная очередь. Redis допустим для ephemeral cache, статус задания живёт в PostgreSQL.
- Gateway/cache в своём контуре. Публичный CDN — опция, а не зависимость. Кэш закрытых данных проверяет права до cache hit.
- Immutable manifests и dataset versions; source adapters не зависят от UI. Backup includes metadata, assets, secrets recovery instructions и grid resources.

Подробное решение: [ADR 0001](docs/architecture/0001-self-host-data-and-ingestion.md).

## Как принимаем производительность

Нужны фиксированные CPU/RAM/disks/network и классы browser/GPU, число активных пользователей, сценарии и версия данных. До benchmark это цели, не рекламные обещания:

- Плавность 50–60 FPS на согласованном desktop; отдельная цель для mobile.
- Первый полезный экран p95 до 2 s на согласованной сети; pano preview p95 до 1 s.
- Warm tile p95 до 200 ms, cold tile p95 ориентировочно 0,5–1,5 s по классу.
- Ограниченное потребление памяти независимо от общего размера каталога; отсутствие роста после 100 переходов media и длительной навигации.
- Проверяем одновременно raster + vectors + media + ingestion; cold/warm cache, плотные области, low zoom и private filters.
- Установка, backup restore, worker restart, заполнение scratch и interrupted upload входят в приёмку наряду с FPS.

Объём реальных данных и concurrency уточняются на M0; фиксируем результаты в репозитории. Без этого не выбираем «достаточный сервер» только по TB/числу строк.
